## Why `setsid` and not `nohup setsid`

`launch.sh:72` prefers `nohup setsid bash -c …`, but macOS ships no `setsid`
(`nohup: setsid: No such file or directory`, verified on this host), so this
platform always takes the `launch.sh:75` fallback. The reproduction uses the
fallback because that is what runs here.

# The mechanism (AC-2) — established, at file:line

Four links, each measured on this host, not inferred:

**1. `skills/ilk-launcher/scripts/launch.sh:75` ignores exactly SIGHUP and SIGINT.**

```bash
nohup python3 -c 'import os,sys; os.setsid(); os.execvp("/bin/bash", ["bash","-c",sys.argv[1]])' "$cmd" >"$log" 2>&1 </dev/null &
```

Two independent contributions, decomposed by running the same disposition
probe under each element alone:

| invocation | SIGINT | SIGHUP | SIGTERM | SIGQUIT |
|---|---|---|---|---|
| plain foreground | dflt | dflt | dflt | dflt |
| `nohup`, foreground | dflt | **SIG_IGN** | dflt | dflt |
| `&`, no `nohup` | **SIG_IGN** | dflt | dflt | **SIG_IGN** |
| `nohup … &` (= `launch.sh:75`) | **SIG_IGN** | **SIG_IGN** | dflt | **SIG_IGN** |

`nohup` contributes SIGHUP; the async list (`&` in a shell without job
control) contributes SIGINT and SIGQUIT. **SIGTERM is untouched by both** —
which is why its three tests never fail.

**2. The disposition survives every `exec` down to pytest.** POSIX `exec`:
signals set to be ignored in the calling process image are set to be ignored
in the new image. So `launch.sh:75`'s `python3` → `bash -c` →
`run_ilk_loop_claude.sh` → the batch gate → `pytest` all carry SIGINT/SIGHUP
ignored. Measured above at the far end of that chain: the probe printed
`{'SIGINT': 'Handlers.SIG_IGN', 'SIGHUP': 'Handlers.SIG_IGN', 'SIGTERM': 'Handlers.SIG_DFL'}`
from inside the detached tree.

**3. `test_scheduler_exit_reason.py:47-52` (`_start_scheduler_poll`) passes the
ignore into the child.** It spawns `subprocess.Popen(["bash", SCHEDULER, ...],
env=sandbox.env)`. `env=` replaces the environment; it does not touch signal
dispositions, and `Popen`'s default `restore_signals=True` only resets the
handlers *Python itself* set to SIG_IGN (SIGPIPE, SIGXFZ, SIGXFSZ) — not
dispositions inherited from the parent. The bash child therefore starts with
SIGINT and SIGHUP ignored.

**4. `scheduler.sh:128-129` then silently fails to install its traps.**
`bash(1)` on this host, line 4665: *"Signals ignored upon entry to the shell
cannot be trapped or reset."* So:

- `scheduler.sh:127` `trap '_scheduler_handle_sig SIGTERM 15' TERM` — installs.
- `scheduler.sh:128` `trap '_scheduler_handle_sig SIGINT 2' INT` — **no-op.**
- `scheduler.sh:129` `trap '_scheduler_handle_sig SIGHUP 1' HUP` — **no-op.**

`trap` returns success either way, so nothing reports the failure.

**Consequence.** `proc.send_signal(SIGINT|SIGHUP)` is delivered to a process
that ignores it. The scheduler stays in `sleep … & wait $!`
(`scheduler.sh:618`), the pidfile is never removed, no signal line is logged,
and `proc.wait(timeout=10)` at `test_scheduler_exit_reason.py:215`, `:243` and
`:273` raises `TimeoutExpired` — the exact failure in all six.

## What this says about the sub-plan's framing

The sub-plan attributed the regression to SP1/SP2/SP4 ("they are red again
after SP1/SP2/SP4") and to full-suite collection order. Both are wrong, and the
reproduction above is what rules them out: the file alone fails with an empty
prefix, and it fails at a commit where the six tests and `scheduler.sh` are
byte-identical to the `02:27` gate that passed.

What differs between the `02:22` fix / `02:27` pass and the `13:58` gate is
**which process launched pytest** — not the code. A gate run from an operator
shell traps all three signals; a gate run inside the launcher's detached tree
traps only SIGTERM. This is a latent condition the tests were always subject
to, surfaced by *where the gate ran*, and calling it a batch regression would
have sent step 2 looking for a leak that does not exist.

It remains correct not to add the six to `ship.baseline_red` (AC-6): they are
fixable, and step 2 fixes them.

## Why the six only failed "in company" — the last link

Measured from inside the live loop tree during this sub-plan (this iteration's
own ancestry, `run_ilk_loop_claude.sh` pid 91866 → 92021 → `gtimeout 1800s` →
`claude -p` → the agent's shell):

- The **batch gate** is spawned directly by the driver shell at
  `run_ilk_loop_claude.sh:1365`, so it inherits the launcher's SIG_IGN. Hostile.
- The **agent's own** `pytest` runs are spawned behind `claude`, and `claude`
  (a Node process, which installs its own SIGINT/SIGHUP handlers) hands its
  children SIG_DFL again. Benign.
- `gtimeout` is **not** the resetter — probed directly: under the detach,
  dispositions are `SIG_IGN` both directly and via `gtimeout 20s`.

So "in company" never meant *other tests*. It meant **run by the driver rather
than by the agent** — which is why every scope the agent could measure by hand
was green, and only the gate was red. Any bisect over test selections would
have searched a space that does not contain the cause.

The new AC-5 test does not depend on any of this: it sets SIG_IGN in the pytest
process itself, so it reproduces the hostile condition in either ancestry.
